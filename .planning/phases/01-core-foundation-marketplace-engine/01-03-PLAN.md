<objective>
Implement the core contract marketplace engine and bilateral status state machine: Outgoing and Incoming contract creation with strict validation, concurrency-safe single-claim locking using PostgreSQL row-level locks, creator claim approval, in-game dispatch and acceptance reporting, bilateral completion verification, cancellation handling, and comprehensive concurrency integration tests.
</objective>

<threat_model>
ASVS Level 1:
- Concurrency / Race Conditions: Two users claiming the same listing concurrently must be serialized using `SELECT ... FOR UPDATE` inside a database transaction, returning HTTP 409 Conflict for the losing request.
- State Machine Tampering: State transitions must enforce strict access control (only creator or accepted claimant can execute valid transitions). Unauthorized actors attempting to transition status must receive HTTP 403 Forbidden.
- Input validation: All airport codes must exist in the `airports` table; aircraft classes must be valid enum values (A–F).
</threat_model>

<task id="T2">
  <action>
    Implement `src/services/contract.service.ts` with strict transactional concurrency and state machine logic:
    - `createListing(creatorId, input)`: inserts listing with status 'open' and expires_at.
    - `claimListing(listingId, claimantId)`:
      - Uses a PostgreSQL transaction with `SELECT ... FOR UPDATE` on the `listings` row.
      - Checks `listing.status === 'open'`. If not open, throws HTTP 409 Conflict ("Listing already claimed or closed").
      - Verifies `claimantId !== listing.creator_id` (cannot claim own listing).
      - Inserts `listing_claims` record with status 'pending'.
      - Updates listing status to 'claimed'.
      - Inserts audit record in `status_events` ('open' -> 'claimed', event_type: 'claimed').
    - `approveClaim(listingId, creatorId, claimId)`:
      - Validates caller is `creator_id` and listing status is 'claimed'.
      - Updates claim status to 'accepted'.
      - Updates listing status to 'in_progress'.
      - Inserts audit record in `status_events` ('claimed' -> 'in_progress', event_type: 'approved').
    - `reportDispatched(listingId, actorId)`:
      - Verifies caller is the flight sender (for outgoing: creator; for incoming: claimant).
      - Verifies listing status is 'in_progress'.
      - Records `dispatched_woa` status event.
      - If recipient has also already reported accepted, marks listing as 'completed'.
    - `reportAccepted(listingId, actorId)`:
      - Verifies caller is the flight recipient (for outgoing: claimant; for incoming: creator).
      - Verifies listing status is 'in_progress'.
      - Records `accepted_woa` status event.
      - If sender has also already reported dispatched, marks listing as 'completed'.
    - `cancelContract(listingId, actorId, reason)`:
      - Verifies caller is creator or accepted claimant.
      - Updates listing status to 'cancelled'.
      - Updates active claim status to 'cancelled'.
      - Inserts audit record in `status_events` with cancellation reason.
  </action>
  <verify>
    npx tsc --noEmit src/services/contract.service.ts
  </verify>
</task>
